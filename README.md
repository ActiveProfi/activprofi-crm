# АктивПрофи CRM

Серверная CRM студии. Интерфейс на русском: лиды и базы по группам результатов, воронки, проекты, задачи, дорожные карты, онлайн-доска, роли и персональные права.

Данные команды лежат в SQLite на сервере. В браузере больше не хранится рабочая база. В репозитории только код и синтетические демо-данные: реальных лидов, переписок и клиентских файлов здесь нет.

Нужен Node.js 22 или новее. Отдельные пакеты ставить не нужно: сервер использует встроенные средства Node.js, пароли хэшируются через `scrypt`, база — встроенный SQLite (`node:sqlite`). Позже ту же схему можно перенести на PostgreSQL: таблицы описаны обычным SQL, а обращение к базе собрано в `server/db.cjs`.

## Шаг 1. Настроить окружение

В корне репозитория:

```sh
cp .env.example .env
```

Откройте `.env` и замените `ADMIN_PASSWORD` на свой пароль (не короче 8 символов). Файл `.env` не коммитится. Не вставляйте пароли и ключи в код.

По умолчанию сервер слушает только `127.0.0.1`.

## Шаг 2. Запустить

```sh
node server/index.cjs
```

Или `npm start`. Откройте http://127.0.0.1:3212/ .

Если база пустая и в `.env` заданы `ADMIN_LOGIN` и `ADMIN_PASSWORD`, при первом запуске создаётся администратор. Повторно создать или сменить пароль администратора:

```sh
node server/create-admin.cjs
```

Логин и пароль читаются из `.env`. Сам пароль в консоль не печатается.

## Шаг 3. Войти

На экране входа укажите логин и пароль администратора. Сессия хранится в httpOnly-cookie. Кнопка «Выйти» в правом верхнем углу завершает сессию.

Права проверяются на сервере при каждом запросе:

| Роль | Что видит |
| --- | --- |
| Админ | Всё, настраивает роли и персональные права |
| РОП | Все лиды отдела, импорт баз и распределение |
| Менеджер | Только своих клиентов и лидов. Отметка «Новичок» убирает выгрузки, неизвестные звонки и рассылки |
| Проджект | Свои проекты, назначение исполнителей и создание проектов |
| Руководитель разработки | Все проекты и все задачи, назначает разработчиков |
| Разработчик | Проекты, в которых участвует, и только свои задачи |

Персональный запрет или разрешение перекрывает роль до указанной даты, как в прототипе.

## Шаг 4. Демо-данные (необязательно)

Только в пустую базу и только синтетические контакты `@example.test`:

```sh
# в .env
SEED_DEMO=1
SEED_PASSWORD=demo-change-me
```

Затем, если пользователей ещё нет:

```sh
node server/seed-demo.cjs
```

Либо просто запустите сервер: пустая база с `SEED_DEMO=1` заполнится сама. Пароль администратора берётся из `ADMIN_PASSWORD`, пароль остальных демо-сотрудников — из `SEED_PASSWORD`.

| Логин | Роль |
| --- | --- |
| значение `ADMIN_LOGIN` (обычно `admin`) | Админ |
| `maria` | Проджект |
| `svetlana` | Проджект |
| `elena` | Менеджер |
| `oleg` | Менеджер |
| `irina` | РОП |
| `nikita` | Менеджер, отметка «Новичок» |
| `dmitry` | Проджект |
| `pavel` | Руководитель разработки |
| `anna`, `alexey` | Разработчики |

После проверки поставьте `SEED_DEMO=0`. Повторный запуск демо-скрипта не затирает базу, в которой уже есть пользователи.

## Шаг 5. Перенести данные из браузерного прототипа

Старый прототип держал базу в `localStorage` браузера (ключ `activprofi-variant-b-v2`).

1. Войдите как администратор.
2. На обзоре или в разделе «Команда и роли» откройте блок «Данные сервера».
3. Если этот браузер ещё хранит прототип, нажмите «Перенести данные этого браузера». Вместе с JSON уйдут и файлы онлайн-доски из IndexedDB.
4. Либо на старом прототипе сохраните JSON вручную и нажмите «Загрузить JSON».

Кнопка «Скачать JSON» выгружает текущую серверную базу без паролей. Загрузка доступна только администратору. Пароли уже существующих сотрудников сохраняются. Новым сотрудникам из файла один раз показываются временные пароли — передайте их лично и не оставляйте в общем чате.

Команда `node variant-b/preview.cjs` по-прежнему открывает старую статическую копию без входа. Для совместной работы используйте `node server/index.cjs`.

## Возможности

- Импорт Excel/CSV: файл читается в браузере, на сервер уходят строки. Сервер сам отбрасывает дубли по телефону, email и ссылке на профиль.
- Базы по группам результатов: «Прислать КП», «Перезвонить», «Не актуально», «Уже есть решение», «Отказ», «Требуют проверки».
- Внутри группы — отдельные базы с названием и датой файла.
- Воронки, распределение по менеджерам, проекты, задачи, дорожные карты, онлайн-доска, материалы. У каждой воронки есть этап «Отказ»: без него воронка не сохраняется. Уже существующим воронкам этот этап добавляется сам, старые сделки на него не переносятся.
- Карточка клиента, сделки, проекта или задачи сохраняется отдельно. Правка чужой карточки больше не мешает сохранить свою. Если ту же карточку уже изменили, текст в форме остаётся, его можно перенести заново.
- После успешной сделки карточка становится проектом и попадает на доску «Разработка»: Начало проекта, три релиза, доработка, внедрение, обучение, техподдержка.
- Роли и персональные права.

Телефония, Telegram, голосовой обзвон и отправка писем по-прежнему не подключены: интерфейс готовит карточку, звонок или письмо, но наружу ничего не отправляет. Таблица `mailings` есть только как задел, статус в ней может быть лишь `draft`.

## Интеграция «Исток»

Парсер лидов (отдельный Python-сервис для VK и Telegram) передаёт найденные контакты по ключу.

1. Войдите как администратор.
2. Создайте ключ запросом `POST /api/integration-keys` с телом `{"name":"Исток"}` и заголовком `X-Requested-With: ActivProfi` (из браузера это же делает сессия). Ответ содержит поле `key` один раз. В базе хранится только SHA-256 ключа.
3. Ключ передаётся заголовком `Authorization: Bearer apk_...` или `X-API-Key`.
4. Отозвать ключ: `DELETE /api/integration-keys/{id}`.

Приём лидов без этапа — в общую базу, как раньше:

```sh
curl -s -X POST http://127.0.0.1:3212/api/integrations/leads \
  -H "Authorization: Bearer apk_ВАШ_КЛЮЧ" \
  -H "Content-Type: application/json" \
  -d '{"batchName":"Исток · тест","leads":[{"name":"Иван Пример","vk":"https://vk.com/id1","telegram":"@example","phone":"+79990000000","email":"ivan@example.test","comment":"Интересовался CRM","postUrl":"https://vk.com/wall-1_2","source":"Исток","date":"2026-11-02"}]}'
```

Тело может быть и просто массивом лидов. Если этап не указан, лиды попадают в базу без менеджера, чтобы их распределили в CRM. Компания, сайт и другие контакты сохраняются. Город, сегмент и внешний номер `istokId` тоже записываются в карточку. Телефон сравнивается одинаково в виде `8…`, `+7…`, с пробелами и без них. Повтор того же телефона, email или профиля не создаёт вторую карточку: к существующей добавляются новые телефоны, почты и ссылки и заметка «обновлено из Истока». Этап, менеджер и воронка при этом не меняются.

Ответ в режиме базы:

```json
{"received":2,"created":1,"updated":1,"skipped":0,"ids":["id-нового","id-старого"],"deals":[{"id":"id-нового","name":"Иван","status":"created"},{"id":"id-старого","name":"Иван","status":"updated"}]}
```

Ключ бывает двух видов. При создании в «Команда и роли» → «Ключи Истока» выберите одно:

| `scope` | Что можно |
| --- | --- |
| `leads:write` | Присылать лиды. Забирать выборки этим ключом нельзя. |
| `export:read` | Забирать выборки и выгрузку. Присылать лиды этим ключом нельзя. |

Старые ключи без пометки работают как `leads:write`.

Менеджер в «Клиентах» фильтрует этап, базу, источник и менеджера и нажимает «Отправить в рассылку». В список попадают только клиенты, которых он видит. Новичок и обычный менеджер не добавят чужих. Клиент с отметкой «не писать и не звонить» не попадает. Сама рассылка из CRM не отправляется.

Исток забирает новые выборки ключом `export:read`:

```sh
curl -s "http://127.0.0.1:3212/api/integrations/selections?status=new" \
  -H "Authorization: Bearer apk_КЛЮЧ_ВЫБОРОК"

curl -s "http://127.0.0.1:3212/api/integrations/selections/ID?format=csv" \
  -H "Authorization: Bearer apk_КЛЮЧ_ВЫБОРОК"

curl -s -X POST "http://127.0.0.1:3212/api/integrations/selections/ID/ack" \
  -H "Authorization: Bearer apk_КЛЮЧ_ВЫБОРОК"
```

Колонки CSV по порядку: Название, Контакт, Телефон, Email, VK, Telegram, Сайт, Город, Комментарий, CRM-ID. Файл в UTF-8 с меткой BOM, чтобы Excel открыл русские буквы. Разделитель — запятая. Комментарий собирается из этапа, последней заметки и заметки по статусу.

После `ack` выборка получает статус «забрана». Повторный `ack` не ломает список.

Общая выгрузка тем же ключом, без заранее собранной выборки:

```sh
curl -s "http://127.0.0.1:3212/api/integrations/export?stage=Новый&source=Исток&since=2026-11-01&format=csv" \
  -H "Authorization: Bearer apk_КЛЮЧ_ВЫБОРОК"
```

CRM сама в Исток не обращается. Запросы всегда начинает Исток.

Если лид пришёл сразу на этап, CRM назначает менеджера по правилу распределения. Свободных менеджеров нет — лид появляется у администратора и руководителя отдела в блоке «Ждут менеджера».

После выигранной сделки проект берёт срок и сумму из брифа, почту — в адресаты, текст «что продали» — в описание. Руководитель и проджект подставляются из «Команда и роли» → «Назначения». Сегодняшняя дата сама в срок не ставится. Проекты без руководителя или проджекта видны им в блоке «Новые проекты без команды».

У роли «Проджект» по умолчанию есть права «Создание проектов» и «Назначение исполнителей». Уже созданным ролям эти права добавляются при следующем открытии базы, остальные права не сбрасываются.

Колокольчик в шапке показывает непрочитанное: новую задачу исполнителю, «На проверке» проверяющему, возврат на доработку исполнителю, проект без команды руководителю и проджекту, назначенный лид менеджеру, пропущенный звонок владельцу или дежурному. У задачи есть поле «Проверяет». Если в `.env` задан `TELEGRAM_BOT_TOKEN` или бот уже подключён в CRM, сотрудник привязывает свой Telegram кодом из колокольчика. Сам токен в программу и в чат не вставляйте. Без токена уведомления остаются только в колокольчике.

На обзоре у администратора и руководителя отдела продаж — лиды без менеджера, пропущенные звонки, просроченные контакты, новые лиды из Истока, воронка по этапам и деньги за месяц.

Остаток по сделке равен сумме сделки минус оплаченное. Счёт больше суммы сделки программа не записывает, пока это не подтвердят. То же перед тем, как коммерческое предложение изменит сумму сделки.

В «Отчётах» есть выставлено, оплачено и долг по клиентам и менеджерам за период. В проекте видно, сколько оплачено из бюджета. Сумма сделок разделена на «в работе», «успешные» и «отказ». Готовность проекта считается по всем его задачам и одинакова у всех; «ваши задачи» показаны отдельно.

В задаче кнопка «Записать время»: часы, дата и комментарий. Сумма сравнивается с оценкой. Отчёт «Часы по людям и проектам» и карточка проекта показывают часы и стоимость по ставке часа из «Назначений».

«Отправить в рассылку» сначала показывает список и число людей. Кто уже на этапе «В проекте», не попадает, пока не включить галочку.

Роли короче. «Менеджер-стажёр» больше нет: такой человек становится менеджером с отметкой «Новичок». Новичок не видит чужие лиды, не выгружает базы, не видит неизвестные звонки и не собирает рассылки. «Руководитель проекта» и «Проджект-менеджер» сведены в «Проджект»: свои проекты, назначение исполнителей и создание проектов. «Начальник разработки» называется «Руководитель разработки» и видит все проекты. Персональные права при переносе сохраняются.

У проекта один этап — с доски «Разработка». Одинаковые этапы двух воронок называются одинаково, в фильтре клиентов этапы сгруппированы по воронкам. Старые сделки остаются на своих этапах, меняется только название. Группы «Базы лидов» нужны только чтобы разобрать файл до переноса в воронку.

Вариант КП отмечается, когда клиент согласился, в окне «Передать в проект». Если сделку уводят с «В проекте», программа спрашивает: проект остановить или удалить. Этап «Сдан» хранит дату, номер акта и срок поддержки, после него менеджеру ставится напоминание о допродаже.

У клиента одна лента: письма, Telegram, звонки и заметки. У проекта отдельная лента команды. Старые заметки, письма, звонки и обсуждения остаются и показываются в своей ленте.

Задачу или дело по клиенту можно поставить в карточке, не создавая проект. Они попадают в «Кого не забыть» и в колокольчик. «Заявка в поддержку» на карточке или из письма и Telegram в ленте создаёт задачу в проекте, если сделка уже передана.

Кнопки, которые ещё никуда не звонят и ничего не пишут, спрятаны: черновик нейросети, обзвон и конференция. «Дорожные карты» открываются из карточки проекта, в меню их нет.

События телефонии принимаются только с ключом. В настройках сервера задайте `SIPUNI_WEBHOOK_TOKEN` и добавьте тот же ключ в адрес событий Sipuni параметром `token`. Сам ключ в программу и в чат не вставляйте. Незнакомый входящий номер уходит дежурному из «Назначений» или по очереди. Новичок его не видит.

### Сделка сразу в этап воронки

Так другой помощник может создать сделку, например после звонка колл-центра. Этап задаётся на весь запрос полем `stage` (название, как в воронке) или `stageId`. То же поле можно указать у конкретного лида — тогда оно важнее общего.

Воронка продаж уже содержит этап «Отправлено КП»: он стоит после начального этапа и перед успешной сделкой. У старых карточек этап не меняется.

```sh
curl -s -X POST http://127.0.0.1:3212/api/integrations/leads \
  -H "Authorization: Bearer apk_ВАШ_КЛЮЧ" \
  -H "Content-Type: application/json" \
  -d '{"pipelineId":"inbound","stage":"Отправлено КП","leads":[{"name":"Ирина Колл","description":"Сеть кофеен, нужен учёт заявок","email":"irina@example.test","phone":"+79995550199","source":"колл-центр","date":"2026-11-18","clientTask":"Автоматизировать приём заявок с сайта","kpVariants":"Базовый 90 000 ₽ / 3 недели; Расширенный 160 000 ₽ / 6 недель","kpLink":"https://kp.example.test/maya","callAt":"2026-11-20T15:00","statusNote":"ждём решения","comment":"Просили смету на два варианта"}]}'
```

Поля одной сделки:

| Поле | Что это |
| --- | --- |
| `name` | Имя клиента |
| `description` | Коротко, кто это и что нужно |
| `email` | Почта |
| `phone` | Телефон. Нужен телефон, почта или профиль VK/Telegram |
| `source` | Откуда заявка, например `колл-центр` |
| `date` | Дата сделки, формат `2026-11-18` |
| `clientTask` | Задача клиента |
| `kpVariants` | Варианты КП: суммы и сроки, обычным текстом |
| `kpLink` | Ссылка на интерактивное КП, начинается с `https://` |
| `callAt` | Дата и время созвона, например `2026-11-20T15:00` |
| `statusNote` | Заметка по статусу, например `ждём решения` |
| `comment` | Комментарий, попадёт в карточку |
| `stage` | Этап этой сделки, если он отличается от общего |

`pipelineId` можно не передавать: тогда берётся `INTEGRATION_PIPELINE_ID` из настроек, воронка `outbound` или первая воронка.

Ответ, если сделка создана одна:

```json
{"created":1,"duplicates":0,"errors":0,"batchId":"","id":"идентификатор-сделки","ids":["идентификатор-сделки"],"deals":[{"id":"идентификатор-сделки","name":"Ирина Колл","status":"created"}]}
```

Номер сделки — поле `id`. Если в запросе несколько новых сделок, их номера лежат в `ids`, а подробности — в `deals`. Повтор того же контакта не создаёт вторую карточку: у этого элемента `status` будет `duplicate`, а `id` — номер уже существующей сделки. Неизвестный этап возвращает ошибку, карточка не создаётся. Рассылку этот запрос не запускает.

## API для интерфейса

Все запросы, кроме приёма лидов по ключу, требуют сессию. Изменяющие запросы из браузера дополнительно отправляют заголовок `X-Requested-With: ActivProfi`.

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET /api/workspace`, `PUT /api/workspace` — рабочее состояние с учётом прав и номера версии
- `GET/POST /api/users`
- `GET/POST /api/clients`, `GET/PATCH /api/clients/:id`
- `GET /api/lead-batches`, `POST /api/lead-batches/import`, `POST /api/lead-batches/:id/distribute`, `POST /api/lead-batches/:id/promote`, `POST /api/lead-batches/:id/group`
- `GET/POST /api/pipelines`
- `GET/POST /api/projects`, `GET/PATCH /api/projects/:id`
- `GET/POST /api/tasks`, `GET/PATCH /api/tasks/:id`
- `GET/POST /api/materials`, `GET/POST /api/messages`
- `PUT/GET /api/files/:id` — файлы доски, до 20 МБ
- `GET/POST /api/integration-keys`, `DELETE /api/integration-keys/:id` — у нового ключа поле `scope`: `leads:write` или `export:read`
- `POST /api/integrations/leads` — только ключ `leads:write`
- `GET /api/mailing-selections`, `POST /api/mailing-selections` — выборки для рассылки, по сессии
- `GET /api/integrations/selections?status=new`, `GET /api/integrations/selections/:id?format=csv|json`, `POST /api/integrations/selections/:id/ack`, `GET /api/integrations/export` — только ключ `export:read`
- `GET /api/migration/export`, `POST /api/migration/import`

Чужие лиды менеджеру не отдаются: и список, и карточка по id. Сохранение не умеет стирать чужие записи, которых у пользователя нет на экране.
